# Payments and refunds

Product orders and motorcycle reservations each create a database-backed pending payment. A pending row is **not** a successful charge or deposit. Checkout and reservation amounts are calculated in SQL.

`src/lib/payments.ts` defines `PaymentProvider`. `SandboxProvider` only creates a pending reference and rejects refunds. `GatewayProvider` describes configurable HTTPS initiation and refund contracts. Both send a stable idempotency key. It is not an integration certified for any Egyptian provider. `POST /api/payments/[id]/start` requires ownership and claims an initiation before calling a gateway. The checkout URL and provider reference are persisted so a repeated click returns the same session. `POST /api/payment-webhook` checks a hex HMAC SHA-256 signature over the raw JSON body. The event includes ID, payment ID, provider reference, EGP amount, currency, and status; the database verifies amount, currency, reference, and idempotency before updating payment and parent state.

Return approval or a paid reservation cancellation can create a refund request. Staff with payment and relevant workflow permissions may start it through `POST /api/refunds/[id]/start` when a gateway is configured. A verified `POST /api/refund-webhook` event completes the financial status and case history; failed attempts can be retried with audit history. The browser and staff cannot mark a refund successful. InstaPay remains a pending reference/verification design.

Both webhook routes require `x-revora-signature`, a lowercase or uppercase hex HMAC SHA-256 of the exact request body using `PAYMENT_WEBHOOK_SECRET`. The refund payload contains `event_id`, `refund_id`, `provider_reference`, `amount_egp`, `currency: "EGP"`, and `status` (`pending`, `succeeded`, or `failed`). Duplicate event IDs are accepted only for the same refund and identical financial data. Payment and refund event tables reject updates and deletes.

`POST /api/tasks/expire-reservations` runs both unpaid reservation and order expiration. Call it from a trusted scheduler with `Authorization: Bearer <REVORA_TASK_SECRET>`; it uses the server-only service role. The scheduler must be configured for the chosen deployment platform. Expiration releases motorcycle and stock reservations; authorized payments remain held for reconciliation.

The user has deferred provider selection. To enable live Visa/Mastercard or InstaPay, select a licensed provider, adapt initiation/status/webhook/refund APIs to its actual contract, map event signatures and reconciliation rules, run provider sandbox tests, complete PCI/legal review, and configure `PAYMENT_PROVIDER`, `PAYMENT_GATEWAY_URL`, `PAYMENT_GATEWAY_REFUND_URL`, `PAYMENT_GATEWAY_SECRET`, `PAYMENT_WEBHOOK_SECRET` and server-only `SUPABASE_SERVICE_ROLE_KEY` as applicable. The current generic adapter is insufficient for live traffic.
